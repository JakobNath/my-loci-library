# Decisions: Sync with GitHub

Moved word for word from `HOW_IT_WORKS.md` on 10 November 2026, in their original order (oldest first). Add new decisions on this topic at the end, in the same form: a bold title with the date, then the choice and the reason.

- **Sync, as built (2026-11-10).** All GitHub code is in `edges/sync-github.js`. Each device keeps the fingerprint (Git's blob SHA-1) of every record file it holds; a sync lists the repository's files once and downloads only those whose fingerprint differs. A first download starts from `catalog.json` and works out each record's fingerprint on the device, so files unchanged since the catalog was built are not downloaded at all. Changes made on the device are sent as one commit (records and pictures together) a few seconds after the last save, on start, on "Sync now", and when the connection returns. A sync key and the repository name are kept in this device's settings only (localStorage). The sync module loads just after the first screen appears, the first time it is needed, which keeps opening fast and the app within its size budget.
- **No device overwrites another (2026-11-10).** The two-device test found that a commit built on top of whatever was newest on GitHub silently overwrote another device's change to the same record. A device now builds its commit on the version it last downloaded; if another device has committed since, GitHub refuses, and the device downloads, merges field by field (newest edit wins), and sends again (up to three times).
- **Pictures and sync (2026-11-10).** Pictures taken or downloaded on a device are sent with its next commit (thumbnail, detail image, and the master for our own photos, into `images/thumb/`, `images/detail/` and `images/master/`). Phones never download masters. After each sync a device fetches, in the background, the thumbnails of all physical books it does not yet have; other pictures (detail images, Logos thumbnails) are fetched the first time they are shown, and kept.
- **Settings sync as one small file (2026-11-10).** Changing a shared setting marks settings.json as unsent; the next sync sends it with the records. If both devices changed settings before syncing, this device's settings win; settings change rarely, so a field-by-field merge would add code for almost no gain.
- **The backup status reaches the app through the data repository (2026-11-10).** `loci-backup` writes `backup-status.json` (last mirror, last snapshot, last archive, first backup) and commits it with the daily run; sync downloads it when it changes; Settings shows the last backup, and the yearly archive reminder appears in Settings and, at most once a week, when the app opens. The reminder counts a year from the last archive, or from the first backup until there is one. The yearly archive itself is `loci-backup --archive <folder>`: every file including covers, the exports, and the whole Git history as one bundle file.
- **Connecting to another catalog empties the device first (2026-11-10, moving to the real catalog).** A device kept its own records when it was connected to a different data repository, and its next sync would have sent them there, so moving a phone from the test catalog to the real one would have filled the real catalog with sample books. Now, when a device already connected to one repository is connected to another, the app checks the new repository and key first (a typo changes nothing), then asks with the browser's plain `confirm()` question, naming how many records will leave the device and any unsent changes that would be lost. On OK it empties its own copy (records, pictures, unsent changes, shared settings, fingerprints, backup status) and downloads the new catalog; keys and device settings stay. A device connecting for the first time still keeps and sends its records, as PLAN.md's "Sync" expects. Clearing the browser's site data by hand, the earlier README advice, was rejected: it is easy to get wrong in an iPhone home-screen app and erases the keys too. `confirm()` was chosen over a drawn dialog because it is Baseline, needs no code or styles, and no other screen asks a two-button question.
- **Clearer messages when moving to another catalog (2026-11-10, moving to the real catalog).** The first phone switch failed with GitHub's general "did not let this key read or write" message, because the key box was left empty and the old key, made only for the test catalog, was used. Each GitHub key opens only the repositories picked when it was made, so the app now says so before asking GitHub: when the key is unchanged, it asks for a new key made for the new repository; when GitHub refuses a new key, it names the repository and the step to repeat ("Only select repositories", then pick it). Settings now starts its sync line with the catalog's name, so a device shows which catalog it uses. Guessing the repository from the key was rejected: it needs more of GitHub's API and more code for a step done once per device.
