# Decisions: Sync with GitHub

Moved word for word from `HOW_IT_WORKS.md` on 10 November 2026, in their original order (oldest first). Add new decisions on this topic at the end, in the same form: a bold title with the date, then the choice and the reason.

- **Sync, as built (2026-11-10).** All GitHub code is in `edges/sync-github.js`. Each device keeps the fingerprint (Git's blob SHA-1) of every record file it holds; a sync lists the repository's files once and downloads only those whose fingerprint differs. A first download starts from `catalog.json` and works out each record's fingerprint on the device, so files unchanged since the catalog was built are not downloaded at all. Changes made on the device are sent as one commit (records and pictures together) a few seconds after the last save, on start, on "Sync now", and when the connection returns. A sync key and the repository name are kept in this device's settings only (localStorage). The sync module loads just after the first screen appears, the first time it is needed, which keeps opening fast and the app within its size budget.
- **No device overwrites another (2026-11-10).** The two-device test found that a commit built on top of whatever was newest on GitHub silently overwrote another device's change to the same record. A device now builds its commit on the version it last downloaded; if another device has committed since, GitHub refuses, and the device downloads, merges field by field (newest edit wins), and sends again (up to three times).
- **Pictures and sync (2026-11-10).** Pictures taken or downloaded on a device are sent with its next commit (thumbnail, detail image, and the master for our own photos, into `images/thumb/`, `images/detail/` and `images/master/`). Phones never download masters. After each sync a device fetches, in the background, the thumbnails of all physical books it does not yet have; other pictures (detail images, Logos thumbnails) are fetched the first time they are shown, and kept.
- **Settings sync as one small file (2026-11-10).** Changing a shared setting marks settings.json as unsent; the next sync sends it with the records. If both devices changed settings before syncing, this device's settings win; settings change rarely, so a field-by-field merge would add code for almost no gain.
- **The backup status reaches the app through the data repository (2026-11-10).** `loci-backup` writes `backup-status.json` (last mirror, last snapshot, last archive, first backup) and commits it with the daily run; sync downloads it when it changes; Settings shows the last backup, and the yearly archive reminder appears in Settings and, at most once a week, when the app opens. The reminder counts a year from the last archive, or from the first backup until there is one. The yearly archive itself is `loci-backup --archive <folder>`: every file including covers, the exports, and the whole Git history as one bundle file.
- **Connecting to another catalog empties the device first (2026-11-10, moving to the real catalog).** A device kept its own records when it was connected to a different data repository, and its next sync would have sent them there, so moving a phone from the test catalog to the real one would have filled the real catalog with sample books. Now, when a device already connected to one repository is connected to another, the app checks the new repository and key first (a typo changes nothing), then asks with the browser's plain `confirm()` question, naming how many records will leave the device and any unsent changes that would be lost. On OK it empties its own copy (records, pictures, unsent changes, shared settings, fingerprints, backup status) and downloads the new catalog; keys and device settings stay. A device connecting for the first time still keeps and sends its records, as PLAN.md's "Sync" expects. Clearing the browser's site data by hand, the earlier README advice, was rejected: it is easy to get wrong in an iPhone home-screen app and erases the keys too. `confirm()` was chosen over a drawn dialog because it is Baseline, needs no code or styles, and no other screen asks a two-button question.
- **Clearer messages when moving to another catalog (2026-11-10, moving to the real catalog).** The first phone switch failed with GitHub's general "did not let this key read or write" message, because the key box was left empty and the old key, made only for the test catalog, was used. Each GitHub key opens only the repositories picked when it was made, so the app now says so before asking GitHub: when the key is unchanged, it asks for a new key made for the new repository; when GitHub refuses a new key, it names the repository and the step to repeat ("Only select repositories", then pick it). Settings now starts its sync line with the catalog's name, so a device shows which catalog it uses. Guessing the repository from the key was rejected: it needs more of GitHub's API and more code for a step done once per device.
- **One key for all devices, and a setup link (2026-11-10, Jakob).** Replaces PLAN.md's "one key per device" and the yearly expiry used since "Sync, as built" (2026-11-10). Setting up phones one by one, each with its own GitHub key, proved too hard, and Jakob asked for a far easier setup with less care for key security, since only the two of us use the app. Now one key, made without an expiry date (GitHub's form is filled in with `expires_in=none`), serves every device. Only the first device is set up by hand; on it, "Share setup link" sends the others a link carrying the catalog, the sync key and the Google Books key after the "#" (never sent to any server), through the phone's share sheet, the clipboard, or a box to copy from. Opening the link connects the device, keeps the usual question before emptying a device that holds another catalog, and replaces the address so the keys leave the address bar and the history. On an app served from `<owner>.github.io` the catalog name is filled in as `<owner>/my-loci-library-data`. Putting the key in the app's own code was rejected: the code is public, so anyone could change or delete the catalog, and GitHub cancels keys it finds in public code. The cost of the change: anyone holding the link can use the catalog, and losing a phone means making a new key and sending the link again.
- **The key's name carries the date (2026-11-11).** GitHub refuses a new key whose name is already used, and shows a key's code only once, so a person who had made "My Loci Library" before could not make it again. The form is now filled in with "My Loci Library <date>". An old key whose code was not kept cannot be shown again; it can be deleted under GitHub's Settings › Developer settings › Fine-grained tokens.
- **Catching up before "You already have this edition" (2026-11-14, testing day).** Luther's Works 12 was trashed, and two minutes later scanning it again said it was held, and "Add another copy" hung a copy on the trashed book. On one device this cannot happen (tried in the browser: trash, then the same ISBN, gives no such screen), so the phone that scanned had not yet fetched the trash made elsewhere: a phone left open on the Add tab does not sync until it saves, is reopened or comes back to the front. Now opening Add starts a quiet sync, and when a scanned ISBN matches a held book the phone first waits for a sync (a sync already running is waited for, not skipped) and checks again; offline, it asks at once as before. Rejected: syncing every few minutes while the app is open (battery and data for little gain), and re-reading storage when the app comes back to the front (it guards against two open copies of the app on one phone, which Jakob does not use).
- **A broken file is skipped and named, not a stop (2026-11-15, end of alpha, item 1).** One record file that was not valid JSON stopped every sync on every device with the browser's raw "JSON.parse" error (the first audit, screens and sync finding 12). Now a downloaded record file must parse, be the record its path names (its `id` the file name, its `type` the folder, a whole-number `format`), read in this app's format without error, and have a list wherever `DATA_FORMAT.md` has one; a file that fails is left out, the rest syncs, and Settings' sync line names it at every sync, with a note once in each session. Its fingerprint is not kept, so each sync tries it again and a mended file comes down by itself; the device keeps its older copy meanwhile, and a change made on a device writes a whole file over the broken one. A broken `catalog.json` makes a first download fetch every file instead; a broken `settings.json` or `backup-status.json` is named and left out. The list check is there because a record with, say, `"location": "Study"` would be saved on the device and stop the Library from being drawn at every start. Rejected: the full `core/validate.js` check, which would also leave out records that are only incomplete (a work without a title from a laptop tool), so real books would vanish from the phones; and stopping the sync with a clearer message, which still leaves both phones unsynced over one file. "Three conflicts in a row still say Synced", from the same finding, was fixed in 1.14.3 and has a test (`tests/sync-run.test.mjs`).
- **Lists merge item by item (2026-11-16, end of alpha, item 2).** Merging took every field whole from the device that changed it last, so a cover taken on one phone and a spine on the other, before either synced, left the book with one picture (the first audit, finding F5); tags, contents and value history could lose entries the same way. With two versions alone a merge cannot tell "added here" from "removed there", so it now also uses the version both started from: the one this device last synced, downloaded by the fingerprint the device already keeps for each file (Git keeps every version). Only a record changed on both devices needs it, so it costs one download, rarely. Rejected: keeping a copy of every synced record on the phone (more storage, a second place to go wrong) and a stamp on each list item (a data format change for every list). A field changed on one side only now keeps that change even without a stamp, which also settles the audit's other point, that unstamped differences were kept differently on each device. Lists whose order carries meaning (authors, editors, contributors, datings, location) still come whole from one side: a mix of two orders would be neither person's. A book keeps one cover and one spine after a merge, as taking a picture again does.
