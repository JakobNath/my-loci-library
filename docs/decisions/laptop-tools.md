# Decisions: Laptop tools: backup and the Logos importer

Moved word for word from `HOW_IT_WORKS.md` on 10 November 2026, in their original order (oldest first). Add new decisions on this topic at the end, in the same form: a bold title with the date, then the choice and the reason.

- **loci-backup and loci-sizes (2026-11-10).** Both read the laptop's `config.json` in the tools folder (the data repository's folder and the backup folder), which is never committed. The daily run pulls, fills catalog heights, rebuilds `catalog.json` only when a record changed (so a quiet day makes no commit for the catalog), mirrors changed files by size and time, saves a monthly snapshot of the exports and the HTML catalog, and makes one commit of what it changed. The mirror never deletes: a file missing from the repository stays in the backup, since records are never deleted anyway and a lost picture is better kept. `catalog.json` carries no precomputed search text: the app builds it just after the first screen appears (decision of 2026-11-09), so storing it would only double the file.
- **The HTML catalog uses the browser's own colors (2026-11-10).** `catalog.html` is a backup file, not part of the app, and must open on its own anywhere; it uses the system colors `Canvas` and `CanvasText` (light or dark as the reader's device), so no color is hard-coded and the app's design tokens are not needed.
- **The Logos importer, before a real export (2026-11-10).** Jakob's sample export (`inputs/logos-sample.csv`, build step 4.4) has not arrived, so the importer was built and tested with a small made-up export, and the column names Logos uses are a first reading kept in one table (`columns.mjs`, also in the tools README). It accepts commas or tabs, UTF-8 or UTF-16, and "Surname, Given" names. Steps 11.1 to 11.4 stay unticked until it is run on the real file.
- **"Edited in Loci" for Logos fields (2026-11-10).** Every record notes when each field was last edited, but not by whom, so the importer keeps what it last wrote for each resource in `integrations/logos-import.json`. A field still holding that value is the importer's to update; any other value was set by a person and is left alone. The file is in the data repository, so a second laptop sees the same thing.
- **Logos links and covers (2026-11-10).** Suggested links to existing works are listed in a text file on the laptop, each to be changed from "no" to "yes" by a person and confirmed with `--confirm-links`; nothing is linked automatically. Logos covers come from Open Library by ISBN into `images/inbox/`, in batches that carry on where they stopped. The laptop covers page now saves each cover into the app's catalog on the laptop (the same browser, so the same stored catalog), and the app sends it with its next sync; inbox covers are marked as coming from Open Library. Books with no cover keep the app's drawn cover, which already shows the title and author like a citation, so no separate "tile description" is stored.
- **The real Logos export (2026-11-10, build step 4.4).** Jakob exported a collection of 53 resources (from Logos's Collections menu) as CSV: UTF-8 with a byte-order mark, 24 columns: Resource ID, Metadata Version, Metadata Language, Title, Logos Title, Abbreviated Title, Logos Abbreviated Title, Resource Type, Edition, Authors, My Tags, Community Tags, My Rating, Community Rating, Publishers, Publication Date, Electronic Publication Date, Series, Subjects, Languages, File Name, File Version, Last Updated, License. What it changed in the importer:
  - The publisher column is "Publishers". There is no Subtitle column (the subtitle follows the title's first colon, and is split off there) and no ISBN column.
  - Publication dates include "1884–1885", "1993 [2008]" and "n.d."; the first year is taken, and "n.d." is no year.
  - Authors are "Surname, Given" names separated by ";", and include editors (Philip Schaff, for one); the export does not tell them apart, so all are imported as authors and can be corrected in the app.
  - Five columns change with every export without the book changing (Metadata Version, File Version, Last Updated, Community Rating, Community Tags). Keeping them would make every book look edited on every import, so they are left out of the extra Logos data; every other column is kept, including License (Permanent or Temporary) and Subjects.
  - Without an ISBN, covers are found on Open Library by title and first author, and taken only when Open Library's title is the same; in the trial 1 of 8 was found, and the rest keep the app's drawn cover.
  - A Logos book is suggested as the same work as one in the catalog only when the authors agree, or neither has one: the trial suggested eight Romans commentaries as the Epistle to the Romans (a work with no author) until this was added.
- **The backup folder is a mirrored Google Drive folder (2026-11-11).** Drive for desktop can stream My Drive as a `G:` drive or mirror it into an ordinary folder. The backup uses a mirrored folder (`C:\Users\Jakob\My Drive\My Loci Library backup`), because a streamed drive exists only while Drive for desktop is running, and a scheduled backup that starts before it would fail; the mirror also keeps a second full copy on the laptop. The daily task was made with PowerShell's `Register-ScheduledTask` (the command is in the tools README) rather than by hand, with the same settings the README gives: daily at 12:30, run as soon as possible after a missed start, only while Jakob is logged on, since Git and Drive need his session.
- **Naming the tools, resting a refusing source, and checking the sources (2026-11-11, phase 15 step 2).** Every request from `loci-enrich` now carries a User-Agent naming the tools and their repository (Open Library allows three requests a second instead of one to an identified caller; Wikimedia requires it), and the sources' addresses are kept together in `loci-enrich/sources.mjs`, so a source that moves is changed in one place. A source that answers 429 or 403 is not asked again for the rest of the run, and the report names it; its books stay due and are asked next time. `check-sources` asks the sources live about the books recorded for the tests and reports what no longer answers or reads differently, as the yearly contract check in `SOURCES.md`. Its first run, on 11 November 2026, found every source answering and one difference: the Library of Congress no longer returns a record for 9780140449136. The phone needed no change in this step (browsers cannot set a User-Agent; the phone will send `Api-User-Agent` to Wikidata in step 7), so no app version was released for it.
- **The laptop keeps the sources' answers and which source gave each value (2026-11-11, phase 15 step 4).** After an outside review of the sources' future, Jakob chose to keep this on the laptop rather than on every record. `loci-enrich` now writes each book's raw answers to `integrations/answers/<edition id>.json.gz` in the data repository (gzip, because a Library of Congress or HathiTrust answer is tens of kilobytes of text and a whole catalog's would weigh on the repository; any unzip tool opens it), only when an answer changed, so quiet re-checks add nothing to the history. Google Books' answers are read but not kept, since Google's terms do not invite storing its results. `integrations/enrich.json` gains `from` for each book: the source of every value written, found as the first source, in the order asked, whose own answer holds it. A book without an ISBN but with an LCCN or OCLC number (typed by a person) is now asked by that number, of the Library of Congress (LCCN only) and HathiTrust, the two searched by such numbers; it is remembered as `lccn:<number>`. Phones never download `integrations/`: sync reads only the record folders.
- **The tools stop on records newer than they know (2026-11-12).** The app checked for records in a newer data format, but the tools did not: a tool on format 2 that met a format-3 record, edited by a phone already on 1.7.0, would have written it back without the fields it does not know. Every tool now reads records through `readRecords` in `shared/data-repo.mjs`, which stops with "Update the tools first" when any record is newer, before anything is written; `writeRecord` refuses such a record too. The backup's exports pass `allowNewer`, since they never write records and a daily backup should not fail because the phones were updated first. The order for a format change stays: publish the app, then update the tools on the laptop (`git pull` in the tools folder).
- **Logos volumes of known sets (2026-11-12, phase 15 step 8).** A new Logos resource whose series (or the start of its title) names a known set, and whose title names a volume ("Luther's Works, Vol. 31"), is added with that volume's works from the list, its set and its volume, instead of as one work named after the book; no links to existing works are suggested for it. Resources already imported are not changed: filling books already in the catalog from a list is phase 15 step 11. `update-core` now copies the app's `sets/` beside `core/`, and the tools' tests check the two copies agree. The works are made by `recordsForKnownVolume` in `core/known-sets.js`, so step 11 can use the same code.
- **The admin page (2026-11-12, the big run, phase 7).** One page, served on the laptop by `admin/admin.mjs` (Node's own `http` module; `admin.cmd` and `admin.sh` start it and open the browser), at `127.0.0.1:8650` only. How it runs: each button starts the tool's own script as a separate Node process, so the command-line tools stay exactly as they are and a failing tool cannot stop the page; one tool runs at a time. Safety: requests addressed to any other host name are refused, and a tool runs only when the request comes from the page's own address (the browser's `Origin`), so no web site open in the same browser can press a button. How the handbook stays in step: it holds no copy of the documentation. `admin/chapters.mjs` names, for each chapter, a document and a section (`HOW_IT_WORKS.md` "The parts", the tools README, `DATA_FORMAT.md`, `SOURCES.md`…); the page reads them when it opens, from the app's folder beside the tools or, failing that, from the published app, and shows each with "From …; change it there". Only one opening line per chapter is written in `chapters.mjs`. A test checks that every named section still exists, so renaming a heading without updating the chapter list fails the tests. A new section, "Sync between devices", was added to `HOW_IT_WORKS.md` for the sync chapter. The look follows design A (one column, the app's book serif and tokens, served from the app's `styles/tokens.css`), chosen as the safest while Jakob decides between three mockups (STATUS.md, "Open questions"); it prints as a plain handbook. A bug found while trying it: `check-sources` read `wikidata.js` among the recorded books and stopped; it now reads only files named by an ISBN.
- **The shelf planner (2026-11-12, the big run, phase 8).** Shelf widths are not part of any record, so rather than change the data format they are typed on the admin page as plain lines and kept in `integrations/shelves.txt` once an arrangement is recorded. The planner sorts every owned physical copy in the chosen place (author, original date, subject, or title) and fills the shelves in the order given, each to nine tenths of its width (room for a hand and later books), using the size estimate the shelf view uses (measured, spine photo, catalog, or pages). Books keep the order strictly, so a book too wide for the rest of a shelf starts the next one; whatever is left is listed, and such a plan cannot be recorded. Nothing is written while planning; "The books are moved: record their places" asks for confirmation, then writes only copy records (location and shelf order) and the widths, in one commit. It was tried on the test catalog only (`admin.mjs --data`); the real catalog waits for Jakob.
- **Printed shelf lists (2026-11-12, phase 9).** A page of its own (`/print` on the admin server), one table per shelf, in shelf order or by original date, set for paper with the app's tokens; it forces black on white when printed, so a laptop in dark mode still prints a readable list (the one place outside the tokens that names a color). An anthology is listed once, at its earliest date; the app's setting for listing it under each work is not followed here, to keep the paper list one line per book on the shelf. PLAN.md's "read on screen, not printed" was changed to match.
- **The admin page keeps look A (2026-11-12, Jakob).** Of the three mockups (A, one column like a reference book; B, a contents column beside the text under the app's green bar; C, tool tiles with their last run above the handbook), Jakob chose A, the one already built. Nothing changed in `admin/page/admin.css`.
