# Decisions: Data format and records

Moved word for word from `HOW_IT_WORKS.md` on 10 November 2026, in their original order (oldest first). Add new decisions on this topic at the end, in the same form: a bold title with the date, then the choice and the reason.

- **Book sizes for the shelf view (2026-11-09).** Photos give a spine's shape but not its scale, so sizes come from the best source available: measured, catalog, same series, then a typical height for the binding; thickness from a spine photo times the height, or from the page count. Only real values are stored, each with its source. Measuring is optional, through a height box on the spine photo screen; a typed height is never overwritten. Catalog heights come from the Library of Congress through the laptop tool `loci-sizes` (daily with the backup, or by hand), because its catalog service cannot be reached from a web page: it has no encrypted connection and does not allow calls from other sites (checked 9 Nov 2026). Pages are stored as printed and counted by the app, so journal ranges such as "89–132" count as 44. Rejected: a reference sheet of paper in every photo (wrong depth for spines, limits book size, an extra step for every photo).
- **Shelf order, a first guess for Jakob to review (2026-11-09).** Jakob wants the shelf view mainly to show quickly where a book stands, and later to plan arrangements of the library on the laptop. Chosen, as the lightest option that serves both: an optional shelf-order key on each copy (a short string that sorts, so placing one book between two others changes only that one record), filled automatically when batch add scans a shelf from left to right; without it a shelf follows the library's sort order. No reordering by dragging in the phone app. The arrangement planner is a later laptop tool. Rejected for now: a numbered position (inserting a book would renumber and re-sync the whole shelf) and dragging on the phone (more code for a rare task).
- **Image folder named `images/` (2026-11-09).** The build plan spoke of `covers/thumb/` and so on. Since spines are stored too, the data repository uses `images/thumb/`, `images/detail/`, `images/master/` and `images/inbox/` (see `DATA_FORMAT.md`).
- **Edition field `medium` (2026-11-09).** The physical-or-Logos field of an edition is called `medium`, because `format` already names the record format version on every record.
- **settings.json is completed before first use, not versioned (2026-11-10).** The example in DATA_FORMAT.md left out the saved views, which PLAN.md lists. The `views` key was added to format 1 rather than raising the format, because no catalog has a settings.json yet. The file is written by `core/settings.js` with its keys in a fixed order, and any key missing from it takes its default, so a later key never breaks an older file.
- **Data format version 2 (2026-11-10, build step 14.7).** Each edition gained `identifiers` (Library of Congress control number, OCLC number, Library of Congress and Dewey call numbers) and `subjects`, placed after `isbn` and `languages`. Choices made while building it:
  - `migrate` in `core/records.js` upgrades a record as it is read: by the device's storage, by sync after downloading, by `mergeRecords` (so two devices merging versions 1 and 2 never take a missing field as empty), and by the tools' `readRecords`. A version-1 file stays as it is until the record is next saved, so nothing is rewritten only to change its number.
  - `catalog.json` holds each record exactly as its file stores it (the tools' `readStoredRecords`), and `recordToFileText` writes a version-1 record exactly as stored; otherwise a device's first download could no longer tell which files match the catalog and would fetch every one.
  - The app was published (1.1.0) and checked on GitHub Pages before any record was written in version 2. A device still on 1.0.5 that meets version-2 records stops syncing and asks to be reloaded, as designed.
  - The Zotero companion sends the call number only when Loci has one, so the call numbers already on Jakob's Zotero items are never emptied. `loci-enrich` fills each catalogue number on its own and the subject headings when there are none.
  - The CSV export has five new columns (LCCN, OCLC, LC call number, Dewey number, Subjects); the book page shows them under the edition's facts.
- **Data format version 3 planned (2026-11-11).** For phase 15 (PLAN.md), one format change will carry everything the anthology and source work needs, so records change version only once: a work's Wikidata ID and other titles; an edition's Open Library and HathiTrust IDs; short pieces in an edition's contents (title, author, date, pages, original title) beside its works; a "cite" mark on a contents entry, for Zotero sections on demand; and an edition's contents found by the laptop, waiting for a person. Outside identifiers stay fixed, named keys, always in the same order, rather than the free list `{scheme, value, source, date}` an outside review suggested: every file then reads the same, and a reader in 2045 needs no code to understand one. Which source filled which field, and each source's raw answer, are kept by the laptop tools in `integrations/` in the private data repository, not on the records, which keeps records small and the phone fast. The change goes on its own branch, is published to the phones before any tool writes version 3 (as for version 2), and is read by `migrate` without rewriting older files.
- **Data format version 3 built, on a branch (2026-11-12, phase 15 step 6; app 1.6.0, not yet published).** Built on the `format-3` branches of the app and the tools, to be merged and published only after Jakob has looked at it. Choices made while building it:
  - Works gained `otherTitles` (searched) and `wikidata`; editions gained `foundContents` and the identifiers `openLibrary` (from Open Library's edition record) and `hathiTrust` (HathiTrust's record number, the MARC control number); contents entries gained `piece` and `cite`. `migrate` reads version 2 into version 3 with nothing lost, in the fixed key order.
  - A record still in an older version is written with that version's keys only, so its text stays exactly as stored; the first device download can still tell which files match `catalog.json`.
  - A piece is kept in its contents entry (`work` null) rather than as its own file: a poem needs no category, tags or datings of its own, and a Library of America volume would otherwise add about a hundred files. It is searched apart from books, in the folded "Also inside" line, and its date counts in the book's date range. The speed test searches 20,000 pieces: 6 ms in the development browser, against 100 ms on a phone.
  - The checks of a record (`validateRecord`) moved from `core/records.js` to `core/validate.js`, which the app never loads (only the tests and the tools check records), to keep the start-up code within its budget after the new fields: 653 bytes remain.
  - A contents entry made in memory before `cite` existed counts as not cited; the file always gets the key.
