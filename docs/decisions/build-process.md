# Decisions: Build process and working setup

Moved word for word from `HOW_IT_WORKS.md` on 10 November 2026, in their original order (oldest first). Add new decisions on this topic at the end, in the same form: a bold title with the date, then the choice and the reason.

- **No GitHub CLI at the start (2026-11-08).** `gh` was not installed when the build began. All local work for phases 1 and 2 went ahead, and the GitHub repositories were created once `gh` was installed and signed in.
- **Line endings.** Every repository has a `.gitattributes` file that stores text with Unix line endings (LF), so files read the same on Windows and Linux.
- **Local preview server.** ES modules do not load from `file://` addresses, so during development the app is served with any static server (for example `python -m http.server`). Nothing in the app depends on which server is used.
- **Code style adopted, and how its rules meet the plan (2026-11-09).** `CODE_STYLE.md` governs all code from phase 3. Where it met the plan: core takes random bytes and the current time as arguments, because core may not read the clock or randomness; `edges/device.js` keeps device settings and the sync key in localStorage, because only `edges/storage.js` may touch IndexedDB and nothing in it is irreplaceable; lookup edges also fetch cover image bytes, so only they name their service; the search box is never re-rendered while typing, only the result list; the `innerHTML` test accepts `escapeHtml(...)`, numbers, or functions whose names end in `Html`; `edges/`, `ui/` and `main.js` sit at the repo root next to `core/`, and the empty `app/` folder goes.
- **One set of core tests for browser and Node (2026-11-09).** The core tests live in `core/tests/*.tests.js`, each exporting a list of named checks. The browser test page (`tests/index.html`) and Node (`tests/core.test.mjs`, run by `node --test`) both run the same files, so there is one specification, not two. The `.tests.js` ending keeps Node's own file search from running them a second time. The app repository also runs `node --test` for the architecture checks in `tests/architecture.test.mjs`, which need to read the source files and so cannot run in a browser page.
- **package.json with no dependencies (2026-11-09).** A three-line `package.json` (`"private": true, "type": "module"`) in each repository tells Node that `.js` files are ES modules, as browsers already assume. It lists no packages and nothing is ever installed; npm is not used.
- **Development data (2026-11-09).** `tests/load-test-data.html` fills the device's catalog from a `catalog.json` file chosen by hand. It accepts only a catalog marked `"testData": true`, which the test-data generator writes and the real catalog never has, and it never talks to GitHub, so it cannot touch the real data.
- **Releasing a new version (2026-11-09).** Change `VERSION` in `sw.js` (and `APP_VERSION` in `ui/settings.js`) and push. Phones fetch the new files in the background and show "New version · Reload"; nothing changes until it is tapped. Checked on GitHub Pages: the app installed for offline use (33 files cached, served from the device on the next visit), a new release showed the note, and tapping it switched versions and removed the old files. An architecture test checks that `sw.js` lists every file the app loads; it caught one missing file (`core/entry.js`) before any phone used the app.
- **Every script is checked for syntax (2026-11-10).** A mistake in the batch add screen, which loads only when opened, was not caught by any test. An architecture test now runs `node --check` on every script of the app.
- **Interface notes (2026-11-10).** Jakob's observations from testing are kept in `docs/plan/INTERFACE_NOTES.md`, and a review of every screen with him is now step 8.6 of the build plan, so the wider interface improvements are made deliberately, with his answers, rather than piecemeal.
- **Shelf view review later (2026-11-11).** Jakob will review the shelf view once several dozen real books are shelved; it is build step 13.0.
- **Windows line endings for launchers (2026-11-10).** The `.cmd` launchers were written with Linux line endings; Windows reads those, but not reliably. A `.gitattributes` file in the tools repository now keeps `.cmd` files in Windows form and `.sh` files in Linux form on any computer.
