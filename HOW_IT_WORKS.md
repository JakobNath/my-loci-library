# How it works

A plain guide to the parts of My Loci Library and how to fix each one. It is written for someone who remembers nothing about the project.

## The parts

To be written as the parts are built.

## Verified approaches

Results of the phase 4 experiments.

- **4.2 Online covers in the browser (2026-11-09).** Open Library: works. A cover fetched by ISBN (`covers.openlibrary.org/b/isbn/<isbn>-L.jpg?default=false`, which answers "not found" instead of a blank image) could be read into a canvas and saved as JPEG in the browser: 320 × 500 px, 56 KB in, 45 KB out, about 1.3 s including the download. Open Library's large covers are often only about 500 px tall, so the detail image is never enlarged beyond the source. Google Books: blocked. Its cover images do not allow web pages from other sites to read them, so the app cannot compress them. Fallback, as the plan names: when only Google Books has a cover, the app records the cover's address on the edition as waiting, and a laptop tool downloads it into `images/inbox/`, where the laptop covers page compresses it like any other inbox cover. Until then the book shows its drawn cover tile.
- **4.4b Catalog heights (2026-11-09).** From Node, the Library of Congress catalog's SRU service (`http://lx2.loc.gov:210/LCDB`, query `bath.isbn=<isbn>`, MARC XML, field 300) gave a height for 6 of 8 sample ISBNs, to the whole centimeter rounded up ("ix, 312 p. ; 23 cm."), in about 0.2 s each. The same service cannot be reached from a web page (no encrypted connection, no cross-site permission), which is why `loci-sizes` is a laptop tool. Its newer JSON search at loc.gov found none of the sample books.
- **4.1, 4.3 and 4.4: waiting.** 4.1 (many files in one commit from a browser) needs a GitHub key made by Jakob for the test-data repository; 4.3 needs Zotero open; 4.4 needs `inputs/logos-sample.csv`. None of them blocks phase 5.

## Phone test results

Results from `prototypes/phone-test.html`, run on real phones during the design stop.

- **Android 16, Firefox 159 (2026-11-09).** Firefox has no built-in barcode detector, so the bundled decoder was used. It loaded in 345 ms the first time and 65 ms once cached. It read ISBN 9780802867339 correctly in 9.5 s on the first try, including the time spent aiming, and in 2.0 s on the second try. Storage passed: persistent storage was granted, the quota was about 56 GB, 50 MB was written in 1.1 s and read back intact in 0.3 s.
- **iPhone, iOS 18.7, Safari (2026-11-09).** Safari has no built-in barcode detector switched on, so the bundled decoder was used. It loaded in 18 ms and read ISBN 9780802867339 correctly in 1.1 s. Storage passed: the quota was about 39 GB, 50 MB was written in 1.0 s and read back intact in 0.04 s. Persistent storage was not granted in an ordinary Safari tab, which is normal; the plan relies on the home-screen app, which Safari exempts from its seven-day clearing of site data. No change of decoder is needed.

Note for phase 6: the first scan took a while. Things to try then are asking the camera for continuous focus where supported and decoding only the middle band of the frame, where the barcode sits.

## Decisions

Choices made during the build that the plan did not settle, with the reason for each.

- **No GitHub CLI at the start (2026-11-08).** `gh` was not installed when the build began. All local work for phases 1 and 2 went ahead, and the GitHub repositories were created once `gh` was installed and signed in.
- **Line endings.** Every repository has a `.gitattributes` file that stores text with Unix line endings (LF), so files read the same on Windows and Linux.
- **Local preview server.** ES modules do not load from `file://` addresses, so during development the app is served with any static server (for example `python -m http.server`). Nothing in the app depends on which server is used.
- **Barcode decoder: zxing-wasm 3.1.6, reader build (2026-11-08).** The smallest reliable choice that reads EAN-13 in Safari on iPhone, where the browser's own `BarcodeDetector` is still switched off. It is about 1 MB in total and loads only on the scan screen. Android Chrome uses the browser's own detector when it supports EAN-13. Details and the one setting that must never be removed (pointing it at the local `.wasm` file) are in `vendor/README.md`.
- **Prototypes share one engine.** The five design options in `prototypes/` all use `prototypes/shared/proto.js` for behaviour and `prototypes/shared/base.css` for structure. Each option differs only in its own `tokens.css` and `option.css`, so the comparison is about the look, not about different features. The prototypes are throwaway and are not reused in the app.
- **Prototype covers are drawn, not photographed.** Each sample book is shown as a plain tile in roughly the color of its binding, so no outside images are fetched.
- **GitHub Pages serves the files as they are.** An empty `.nojekyll` file in the app repo turns off GitHub's Jekyll processing, so there is no build step on GitHub's side either. Pages publishes the `main` branch from the repository root.
- **Second round of designs (2026-11-09).** Feedback on the first five: options 1 (card catalog) and 3 (warm bookshop) were the favorites, but the look should be more timeless, modern and sleek, with fewer bright digital colors. Options 6 to 8 answer that: refined versions of 1 and 3 and a blend of the two, all in warm neutrals with one muted accent.
- **Third round: a playground (2026-11-09).** Option 7 was the favorite. Rather than guess at more fixed variations, option 9 is option 7 with an Adjust panel that switches colors, paper, title type, shelves, covers, corners, spacing, top bar, laptop menu and logo. Each choice is an attribute on the page that only swaps design tokens, which is the same mechanism the finished app will use, so whatever is chosen can be copied straight into `styles/tokens.css`. The current look is kept in the page address so it can be shared as a link. Ten new "L" logo ideas (modern, cute, classic) were in `prototypes/shared/l-logos.js` (removed when the design was locked; see the Git history).
- **Favorite look (2026-11-09).** Chosen in the playground: forest green main color, honey pop, ivory paper, book serif titles, no shelves, large covers, soft cover shadows, round corners, cozy spacing, colored top bar, menu at the side, bookplate logo. Saved as the "Favorite" starting look in `prototypes/option-9/panel.js` (since removed). Nine more classic L logos were drawn to choose from; the logo is still open.
- **Design locked (2026-11-09).** The favorite look with the ex libris logo was chosen. Its values are now in `styles/tokens.css` and described in `docs/plan/DESIGN.md`. In dark mode the main green was made a deeper forest green as asked, with a separate lighter green for green text so contrast stays above 4.5:1. All other prototype options, the Adjust panel and the unused logo ideas were removed to keep the repository small; they remain in the Git history. One prototype is left, in `prototypes/design/`, and it reads `styles/tokens.css` directly, so it always shows the current design.
- **Photo ideas page (2026-11-09).** At Jakob's request, `prototypes/photos/` explores spine photos alongside covers, with mockups for capture, Library views, the book page, lists, sets and fallbacks. It uses one real cover and spine (Luther's Works volume 4), shrunk in the browser to the planned sizes: cover 3 KB + 48 KB, spine 4 KB + 33 KB. Nothing from it is in the plan yet; `PLAN.md` changes only once the ideas are chosen.
- **Photo capture prototype (2026-11-09).** `prototypes/photos/capture.html` tests finding and straightening a book in a photo with plain JavaScript (`prototypes/shared/autocrop.js`, no AI, no library): learn the background from the photo's edges, try a ladder of thresholds, keep the cleanest central shape, check that its four edges are real edges, then straighten with a perspective transform. On the test set, 9 of 11 photos were found without help; the two light-on-light cases correctly ask for a corner check, and none were saved wrongly. A two-sided photo mat (light and dark) fixes the hard cases. Not in the plan until chosen.
- **Photo lab, round 3 (2026-11-09).** `prototypes/photos/lab.html` replaces composite test photos with real ones only (`prototypes/photos/real/photos.json`, filled from `inputs/photos/`), and measures success against true edges that a person confirms in the page's review step (`real/truth.json`). New: a spine mode that finds two long parallel edges (`shared/spine.js`); edge refinement at full resolution with an error estimate in pixels (`shared/refine.js`), which decides saving without asking (within 2% of a cover's width, 3% of a spine's); an edge-line editor for spines with snapping and a rotate handle (`photos/editor.js`); and enhancement using the surface around the book as a neutral reference (`shared/enhance.js`). Laptop timings in the development browser pane were throttled about sevenfold, so speed is reported from phones. Nothing here is in `PLAN.md` or `DATA_FORMAT.md` until approved.
- **Real test photos (2026-11-09).** 40 photos from `inputs/photos/` are in `prototypes/photos/real/` (reduced to 1,600 px; about 10 MB with the finished images made from them). 29 are uncropped (14 covers, 15 spines; wood table in daylight, one on the duvet) and 11 were already cropped in a phone editor. Checked by eye before review: 12 of 14 covers and 1 of 15 spines saved without asking, none wrongly. Fixes from the real photos: a spine is no longer saved when something (usually a hand) lies across one of its ends; a photo without a camera's exact shape is taken as already cropped; only a light surface is trusted as white for white balance, because dark wood and a dark grey mat cannot be told apart; the even-lighting correction is gentler. The 17 photographed books now appear, with their real photos, in the design prototype and the photo views. Before a release, the test photos could move out of the app repository to keep it small.
- **Measured against the reviewed outlines (2026-11-09).** Jakob reviewed the true edges of all 40 photos (`prototypes/photos/real/truth.json`). Covers: 11 of 14 right without asking (79%), 1 wrong. Spines: 0 of 15 right without asking, 1 wrong, 8 asked that were right. Both wrong saves are the same library book in a clear plastic jacket: the outline followed the plastic, 7.6% of the width outside the board, while the estimated error was 0.2%. A check for a second edge just inside the first was tried and not kept, because a hardcover's hinge groove gives the same signal and 5 of 11 good covers would have asked. Tightening the error bar would not help either, since the edge found is sharp; it is just the wrong one. The estimate is therefore a guard against blurred or broken edges, not against a wrong edge; the result thumbnail with one-tap re-crop remains the safeguard. Spine rates need photos taken lying flat with nothing touching the ends, which this set does not have.
- **Code style adopted, and how its rules meet the plan (2026-11-09).** `CODE_STYLE.md` governs all code from phase 3. Where it met the plan: core takes random bytes and the current time as arguments, because core may not read the clock or randomness; `edges/device.js` keeps device settings and the sync key in localStorage, because only `edges/storage.js` may touch IndexedDB and nothing in it is irreplaceable; lookup edges also fetch cover image bytes, so only they name their service; the search box is never re-rendered while typing, only the result list; the `innerHTML` test accepts `escapeHtml(...)`, numbers, or functions whose names end in `Html`; `edges/`, `ui/` and `main.js` sit at the repo root next to `core/`, and the empty `app/` folder goes.
- **Manual photo capture, not automatic detection (2026-11-09).** Measured on real photos, automatic detection saved covers right 79% of the time on plain backgrounds, spines 0% with a hand in the frame, and made confident wrong saves. Jakob wants any background and the book held in the hand, where detection is weaker still, and every photo needs a look anyway. So the app uses the phone's own camera (no permission prompt, full resolution) and a manual editor with short-range snapping and a magnifier. Enhancement is left out of the app. Rejected: the prototype's detection, confidence and enhancement code (about 900 lines).
- **Speed first; heavy work on the laptop (2026-11-09).** The size budget drops to 100 KB. Bulk cover processing and re-cropping move to a laptop page in a desktop browser (Node cannot decode images without packages); the HTML catalog and `catalog.json` are built by `loci-backup`; phones cache Logos thumbnails only once seen. New speed targets are in `PLAN.md`, with tighter laptop budgets in the tests and the self-test page run on phones.
- **Book sizes for the shelf view (2026-11-09).** Photos give a spine's shape but not its scale, so sizes come from the best source available: measured, catalog, same series, then a typical height for the binding; thickness from a spine photo times the height, or from the page count. Only real values are stored, each with its source. Measuring is optional, through a height box on the spine photo screen; a typed height is never overwritten. Catalog heights come from the Library of Congress through the laptop tool `loci-sizes` (daily with the backup, or by hand), because its catalog service cannot be reached from a web page: it has no encrypted connection and does not allow calls from other sites (checked 9 Nov 2026). Pages are stored as printed and counted by the app, so journal ranges such as "89–132" count as 44. Rejected: a reference sheet of paper in every photo (wrong depth for spines, limits book size, an extra step for every photo).
- **Shelf order, a first guess for Jakob to review (2026-11-09).** Jakob wants the shelf view mainly to show quickly where a book stands, and later to plan arrangements of the library on the laptop. Chosen, as the lightest option that serves both: an optional shelf-order key on each copy (a short string that sorts, so placing one book between two others changes only that one record), filled automatically when batch add scans a shelf from left to right; without it a shelf follows the library's sort order. No reordering by dragging in the phone app. The arrangement planner is a later laptop tool. Rejected for now: a numbered position (inserting a book would renumber and re-sync the whole shelf) and dragging on the phone (more code for a rare task).
- **One set of core tests for browser and Node (2026-11-09).** The core tests live in `core/tests/*.tests.js`, each exporting a list of named checks. The browser test page (`tests/index.html`) and Node (`tests/core.test.mjs`, run by `node --test`) both run the same files, so there is one specification, not two. The `.tests.js` ending keeps Node's own file search from running them a second time. The app repository also runs `node --test` for the architecture checks in `tests/architecture.test.mjs`, which need to read the source files and so cannot run in a browser page.
- **package.json with no dependencies (2026-11-09).** A three-line `package.json` (`"private": true, "type": "module"`) in each repository tells Node that `.js` files are ES modules, as browsers already assume. It lists no packages and nothing is ever installed; npm is not used.
- **Image folder named `images/` (2026-11-09).** The build plan spoke of `covers/thumb/` and so on. Since spines are stored too, the data repository uses `images/thumb/`, `images/detail/`, `images/master/` and `images/inbox/` (see `DATA_FORMAT.md`).
- **Edition field `medium` (2026-11-09).** The physical-or-Logos field of an edition is called `medium`, because `format` already names the record format version on every record.
- **How the size budget is measured (2026-11-09).** The budget counts what a phone loads to open the app (`index.html`, its stylesheets, `main.js` and every module it imports, found by following the imports), and it counts code, not comments. Comments are required on every file by `CODE_STYLE.md`, cost nothing once compressed for download, and a reader in 2045 needs them, so they should never compete with code for budget. Code that the app does not load (the Zotero mapping, used by the laptop tool) is not counted. At the end of phase 5 the app's code is under 100 KB by this measure. Jakob accepted this way of measuring on 2026-11-09.
- **The catalog on a device is one snapshot plus changes (2026-11-09).** Reading 32,000 separate records from IndexedDB took 770 ms in a slowed browser; reading the same records as one stored JSON text and parsing it took 210 ms. So `edges/storage.js` keeps the whole catalog as one snapshot, and each record saved afterwards separately; on start it reads both and lays the changes over the snapshot. Shortly after start, if more than 200 records have changed, they are folded into a new snapshot.
- **Speed tests that know what they are running on (2026-11-09).** The speed tests first time a fixed loop (ten million additions). On a fast machine the laptop budgets apply (search 10 ms, book page 16 ms, opening 300 ms, scroll redraw 16 ms, sorting 100 ms); on a slow one (a phone, or a browser slowed down because its window is hidden) the phone targets from `PLAN.md` apply instead. Each line says which set it used, so a phone's own results are real measurements. In the development browser, which ran about eight times slower than normal, all five passed: search 7 ms, book page 6 ms, scroll redraw 14 ms, sorting 123 ms, opening 577 ms.
- **No service worker on the development server (2026-11-09).** On `localhost` the app does not register its service worker, because cached files would hide each edit; adding `?sw` to the address turns it on for testing offline use locally. On GitHub Pages it is always on.
- **Development data (2026-11-09).** `tests/load-test-data.html` fills the device's catalog from a `catalog.json` file chosen by hand. It accepts only a catalog marked `"testData": true`, which the test-data generator writes and the real catalog never has, and it never talks to GitHub, so it cannot touch the real data.
- **Search on every keystroke (2026-11-09).** A search of 10,000 books takes a few milliseconds, so it runs on each keystroke without waiting for the next screen frame. Only the results are redrawn; the search box itself never is.
- **Releasing a new version (2026-11-09).** Change `VERSION` in `sw.js` (and `APP_VERSION` in `ui/settings.js`) and push. Phones fetch the new files in the background and show "New version · Reload"; nothing changes until it is tapped. Checked on GitHub Pages: the app installed for offline use (33 files cached, served from the device on the next visit), a new release showed the note, and tapping it switched versions and removed the old files. An architecture test checks that `sw.js` lists every file the app loads; it caught one missing file (`core/entry.js`) before any phone used the app.
- **Offline on Firefox for Android (2026-11-09).** Jakob found that the app did not open offline in Firefox on Android. Two fixes, in version 0.5.3: the service worker now matches stored files without regard to the `Vary` header that GitHub Pages sends (some browsers otherwise refuse a stored copy when request headers differ slightly), and it takes charge of open pages as soon as it is installed. The app also says "Ready to use offline" once everything is stored, and Settings shows whether it is, so nobody has to guess when it is safe to go offline. Private browsing tabs never keep apps for offline use.
- **Faster opening (2026-11-09).** Jakob's device took 331 ms to open 10,000 books, over the 300 ms laptop budget. Two changes: the search text of each book is now built just after the first screen appears instead of before it (a search typed in that moment still works, a little more slowly), and sorting compares keys worked out once per book instead of comparing titles with the browser's language rules at every step, which halved the sorting time. Titles still sort with numbers in order (volume 9 before volume 10) and without a leading "The", "A" or "An".
- **Phone targets on every touch-screen device (2026-11-09).** Jakob's phone ran the speed check's counting loop as fast as a laptop, so the tests judged it a laptop and held it to the 300 ms opening budget; it took 331 to 485 ms, because a phone's storage is slower than its processor suggests. The tests now apply the phone targets (opening within 1 second) on any device with a touch screen, and the laptop budgets only on fast devices with a mouse. The self-test page is not stored for offline use, by design; only the app is.
- **Screens loaded when first opened (2026-11-09).** The batch add screen (with the scan camera and the lookups) and the full entry form load the first time they are opened, through one small loader in `main.js`. This goes a little beyond `CODE_STYLE.md`, which names only camera and photo code for loading on demand: without it the app's code came to 128 KB, over the 100 KB budget, and these screens are needed only when adding or editing. Everything else loads at start as before.
- **Batch add, as built (2026-11-09).** A typed ISBN, a USB scanner (which types the ISBN and Enter into the same box) and the camera all lead to the same review card. Open Library is asked first; Google Books only when Open Library knows nothing or lacks authors or publisher. Google Books now refuses all requests without a key (its daily limit for keyless use was zero on 9 November 2026), so Settings has a place for this device's free key. Work suggestions match the title without a leading article and any form of an author's name; nothing is linked unless the person chooses "Same work as". A found Open Library cover is downloaded and compressed after saving, so the next scan is ready at once (measured: 13 ms after Save, against a 200 ms target).
- **Reading lookup answers (2026-11-09).** Pages are taken as printed ("xxviii, 311") and library placeholders ("pages cm", printed before a book's page count was known) are ignored in favour of the plain count. Translators, editors, introductions and illustrators are read from Open Library's "by" line; names keep their initials ("F.J. Sheed").
- **Photos, as built (2026-11-09).** One code path (`edges/photo.js`) reads a photo, straightens it by its four corners, and saves the thumbnail (about 200 px tall), the detail image (about 600 px tall, never enlarged) and, for our own photos, the master (1,600 px on the long side). On a real cover photo this took 114 ms in all on the laptop. Each image also stores its main color and its width-to-height ratio; for a spine photo the ratio gives the book's thickness from its height. While a cover picture loads, its main color fills the space; this takes the place of the "tiny blurred placeholder" in the plan, because a color costs a few bytes in the record and nothing to draw.
- **Laptop covers page (2026-11-09).** `laptop/covers.html` turns inbox covers into the two sizes with the same code as the phone. Saving the results into the data repository needs the sync module, so it arrives with phase 7.
- **Scan signal (2026-11-09).** Jakob found it hard to tell when a scan had worked. Each barcode read now gives a short soft beep, a green glow and "✓ Read <ISBN>" over the camera, and a buzz where the phone allows it (Android; iPhones do not let web apps vibrate). The beep can be turned off in Settings ("Beep when a barcode is read"), as `PLAN.md` lists under the device's scanning settings.
- **Original dates on the review card (2026-11-09).** Jakob's rule is that the first entry should be complete. The card now asks "When was this work written? (not this printing)" every time, unless the linked work already has a date, and the edition's year is labelled "Year of this printing". Saving with no date asks once; "Don't know yet" skips on purpose. Suggestions come from Open Library's record of the work behind the ISBN and its author, reasoned as follows: Open Library's earliest edition is often the first publication (modern books, and translations of modern books), but if it is later than the author's death it is only a printing, and the author's lifetime is suggested instead (Augustine's Confessions: 1482 in Open Library, so 354–430; Chemnitz's Examen: 1596, so 1522–1586); a first publication in the same year as the printing is flagged for checking. Each suggestion says where it comes from and fills nothing until tapped, which keeps the rule that only a person sets original dates; the tapped suggestion's source is kept as the dating's note. Open Library's data has errors (it gives 1928 for Bonhoeffer's Nachfolge, published 1937), which is why suggestions are labelled. The work's title is offered as the original title when it differs (Examen Concilii Tridentini, Nachfolge).
- **More on the review card (2026-11-09).** At Jakob's request: original title, translation first published (when there is a translator), series and number, set and volume, price paid, estimated value, and notes, so most books need no second visit.
- **Batch add, step by step (2026-11-10).** After phone testing Jakob found the single review card clunky, at times wordy and at times unclear, and it did not ask enough. Batch add now asks one question per screen, in the order Jakob chose: is this the book (with "Fix details" for anything missing or wrong), the same work as one already held (only when likely), when the work was written, the cover, a spine photo, the binding, where it goes, and anything else (notes, value, price paid, series, set, translation date). Steps with nothing to ask are skipped; each shows "Step n of N", a short line saying what is wanted, and large answer buttons. The online cover is now downloaded and checked while the person answers the first steps, so the cover step can say "No cover found online" (or "too small to look sharp") and offer a photo, instead of failing quietly after saving. Titles that come back all in lower case are put into title case; titles with capitals of their own are left alone.
- **Phone fit (2026-11-10).** Body text is 16 px and small text 14 px (iPhones zoom in on fields with smaller text), buttons are at least 44 px tall, and the scan camera fills the width (up to 640 px). See `docs/plan/DESIGN.md`.
- **Spine photos shown (2026-11-10).** The shelf view now draws a book's spine photo when it has one, at the book's height and its own shape. On the book page a spine photo stood at its full height and squeezed the cover to nothing; it now takes the cover's height and the width its shape gives (Jakob chose: only a spine photo on the book page, no drawn spine).
- **Every script is checked for syntax (2026-11-10).** A mistake in the batch add screen, which loads only when opened, was not caught by any test. An architecture test now runs `node --check` on every script of the app.
